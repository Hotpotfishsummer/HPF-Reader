## 0. 一句话结论

四项能力里，**翻译的骨架已经存在且质量不错**（`Translator` 接口 + SSE + OpenAI 兼容 + 术语表注入），
**真正缺的是三样东西**：① 后台任务的真实执行（现在只标记 failed）② 成本与配额闸门（现在完全没有）③ 术语表的**服务端持久化**（现在每次请求由客户端现传，跨设备不同步）。

书源（含 Z-Library 类）的**框架**已有表与接口，但**只内置了 Gutenberg 一个源**，用户自配规则没有加载路径。

### 1.2 三个真实缺口（都是「AI 一上线就会立刻爆」的类型）

**缺口 A：后台任务不执行。**
`internal/worker/worker.go:96-114` 的 `process()` 是占位实现，**把任务一律标记 failed** 并写 `not_implemented`。
这是刻意的（注释写明「虚假的 succeeded 会让前端误以为正文已被处理，属于最糟的失败模式」）——**这个判断是对的**，但 M5 必须补上真执行。

**缺口 B：没有成本闸门。**
- `ai_usage` 表从未被 INSERT（全仓 grep 只在 migration 与 RLS 名单里出现）；
- `quota_ai_calls` 只被 `store/auth.go:21` 读进结构体，**没有任何一处比较**；
- 后果：**任何人拿到账号就能无限刷 LLM 调用，账单直接失控**。这不是优化项，是上线前的阻塞项。

**缺口 C：术语表不落库、不同步。**
`TranslateRequest.Glossary` 是每次 HTTP 请求由客户端现传（`httpapi/ai.go:24`）。
后果：手机和电脑各存一份，**用户在人名归一化里确认的译名不会同步到另一台设备**，整书译名一致性直接失效。
这正是用户要的核心价值（「人名归一化」），必须服务端权威存储 + 走现有同步通道。

## 2. LLM 接入

### 2.1 供应商策略（决策）

**默认 DeepSeek + 支持 BYOK + 可选本地 Ollama**，三档同一套 OpenAI 兼容代码，只换 baseURL / model / key。

理由：
- DeepSeek 中文强、便宜、国内直连（不用代理），整书翻译成本极低；
- BYOK 能把成本与合规压力转给用户，是自托管项目的合理默认；
- Ollama 本地跑满足隐私需求，代码零改动（它也是 OpenAI 兼容）。

**不要**做「多供应商抽象层 + 每家用不同 SDK」。现有 `OpenAITranslator` 已经证明一套 OpenAI 兼容协议够用，加抽象层是过度设计。

### 2.2 要补的工程点

1. **重试与退避**：上游 429/5xx 要指数退避 + 抖动，**只对幂等请求重试**。流式已开始吐字后不可重试（否则译文重复），只能报错让客户端重发。
2. **超时分层**：连接超时（短，10s）与首字节超时（中，30s）与整段超时（长，300s）分开。现在只有一个 `http.Client.Timeout`，长文会被误杀。
3. **BYOK 密钥加密存储**：新增 `user_ai_keys` 表，**用信封加密**（每用户 DEK + 主密钥 KEK 来自环境变量），**绝不落明文**。解密只发生在 worker/网关内存里。
4. **用量记账**：每次调用结束（含失败）写 `ai_usage`，记录 feature/model/input_tokens/output_tokens。
5. **配额闸门**：调用前查「本周期已用调用数」，超 `quota_ai_calls` 返回 429 `code=quota_exceeded`，并带 resetAt。**这个必须在进入流式之前判定**，否则已经吐字了再报错很别扭。

### 2.3 Token 计数怎么拿

OpenAI 兼容协议的流式响应**默认不回 usage**。三个办法：
- 请求体加 `stream_options: {"include_usage": true}`（OpenAI 与 DeepSeek 支持，**Ollama 不支持**，需降级）；
- 上游不回时用本地估算：中文约 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token（**粗估，仅用于记账，不用于计费仲裁**）；
- 记账字段标记来源（`usage_source` = upstream | estimated），**不要假装精确**。

## 3. 翻译

### 3.1 三种翻译场景，成本差三个数量级

| 场景 | 触发 | 单次规模 | 说明 |
|---|---|---|---|
| **划词/段落翻译** | 用户选中 | ≤ 2000 字 | 已实现（`handleTranslate`），延迟敏感，必须流式 |
| **整章翻译** | 翻到新章 | 5k–15k 字 | 预取下一章，后台任务 |
| **整书翻译** | 用户显式发起 | 20 万–50 万字 | `book_translate` 任务，必须分块 + 断点续跑 |

### 3.2 整书翻译的关键设计

**分块**：按**章节**切，不按字数切。章内再按段落聚合到 ~2000 字一块，**块边界必须在段落边界**（切断句子会让模型补全，产生幻觉）。

**上下文传递**：每块带「前一块的最后 2 段原文 + 译文」作为 Context，而不是带全书。全书做 context 会超窗口且成本爆炸。

**术语一致性（核心）**：每块都把**当前已确认的术语表**塞进 system 前缀。因为前缀不变，**能命中上游 prefix cache**，成本几乎为零。这是现有 `BuildMessages` 已经做对的事。

**断点续跑**：块级幂等。新增 `book_translation_chunks` 表，记录 (jobId, chapterIndex, chunkIndex) 的状态与译文。中断后从第一个未完成块继续，**不重头再来**。

**预算熔断**：任务开始前按「总字数 × 单价」估算总成本，超过用户设定上限则**拒绝创建任务**并告知预估金额。中途超限则暂停任务（可续），而不是静默烧钱。

### 3.3 译文缓存

同一本书同一块 + 同一术语表版本 + 同一目标语言 = 同一译文。
用 (contentHash, chunkIndex, targetLang, glossaryVersion, model) 做缓存键，存 `book_translation_chunks`。
换设备/重装后**不重新花钱**。

## 4. 人名归一化（这项最容易被低估）

### 4.1 它到底要解决什么

不是「识别人名」，而是**让同一人物在全书的译名一致**。真实痛点：

| 原文写法 | 机器直译可能出现 | 用户期望 |
|---|---|---|
| Mr. Darcy / Darcy / Fitzwilliam Darcy | 「达西先生」/「达西」/「菲茨威廉·达西」 | 统一为「达西先生」 |
| Elizabeth / Lizzy / Eliza | 三种音译 | 统一，且**别名关系要保留**（读者要知道 Lizzy 就是 Elizabeth） |
| He / She（指代） | 中文无法从「他」反推是谁 | 译为「他」即可，但**归一化表要能标注指代归属** |
| 已有官方译名（如《傲慢与偏见》通行译本） | 模型自创译名 | 用通行译名 |

**所以产物不是「人名列表」，而是「实体 + 别名集合 + 标准译名」的三元组。**

### 4.2 推荐路线：LLM 抽取 + 确定性聚类 + 人工确认（混合）

纯 LLM 抽全书的做法在 30 万字规模上**不可靠且贵**：模型会漏、会编、跨块不一致。
纯 NER（spaCy/Stanza/HanLP）中文人名识别对**音译外国人名**（本书的主要场景）准确率低。

**混合方案：**

1. **候选抽取（LLM，按章）**：每章让模型输出该章的专有名词候选（人名/地名/组织），带原文形式与出现次数。**只要候选，不要译文**。
2. **确定性聚类（服务端，零成本）**：对候选做归一化聚类
   - 大小写/标点归一（Mr. Darcy → darcy）
   - 姓氏前缀剥离（Mr./Mrs./Dr./Miss）
   - 全名与短名合并（fitzwilliam darcy 包含 darcy）
   - 音译相似度（Lizzy/Eliza 用编辑距离 + 首字母规则）
3. **LLM 裁决歧义**：只把「聚类后有歧义的组」交给模型（例如 Darcy 和 Darcy's 是否同一人），**成本比全文抽取低一到两个数量级**。
4. **用户确认**：UI 展示「疑似同一人物」分组，用户点确认/拆分/改译名。
5. **回灌术语表**：确认结果写入服务端术语表 → 下次翻译自动生效 → **走现有同步通道下发到所有设备**。

**关键设计**：第 2 步完全确定性、可测、零成本；LLM 只用在「需要语义判断」的地方。这样即使 LLM 抽漏，聚类仍能把 Darcy / Mr. Darcy 合起来。

### 4.3 为什么必须服务端做

- 客户端做 → 每台设备各算一遍，**重复烧钱**；
- 结果不落库 → 换设备丢失，**术语一致性失效**；
- 无法审计 → 用户不知道钱花在哪。

## 5. 书源接入（含 Z-Library 的合规边界）

### 5.1 已有框架

`book_sources` 表已存在（`rules JSONB`、`kind` = builtin/user、`user_id` NULL 表示内置）。
`sources.Registry` 已支持注册多个 `Searcher`，`SearchAll` 并发聚合且**部分失败不影响整体**（这个设计是对的，一个源挂了不该让整个搜索失败）。

**现状缺口**：`book_sources` 表**没有任何读取路径**——内置源是代码里硬编码的 Gutenberg，用户自配规则没有加载逻辑。

> ⚠️ **本节已被 §12 推翻。请先读 `docs/M5-PLAN-LEGAL-CORRECTION.md`。**
> 2026-11-03 我核实到：Legado 仓库代码已被清空、README 只剩法律公告，其开发者因侵犯著作权罪被判刑。
> 「声明式 JSON 书源引擎」的形态与该案被定罪形态同构，**该方案已废弃**。
> 修正后的方案是：**只做 OPDS + 合法公版书库，不做通用抓取引擎**。

### 5.2（已废弃）原计划：只做声明式 JSON 规则，不执行任意 JS

**理由**（这不是洁癖，是安全边界）：
- 规则引擎若支持任意 JS，服务端等于**开放任意代码执行**，一旦被恶意规则利用就是 RCE；
- 声明式规则能覆盖「按关键词搜 → 解析列表 → 取详情 → 取下载链」这一套主流书源模式，**够用**；
- 不执行 JS 也让它**不会变成通用爬虫平台**，法律定性上更清晰。

**规则草案字段**（只列核心，实现时再细化）：

    {
      "name": "example-opds",
      "protocol": "opds",
      "baseUrl": "https://example.org/opds",
      "search": {
        "path": "/search?q={query}",
        "method": "GET",
        "extract": {
          "item": "//entry",
          "title": "title",
          "author": "author",
          "link": "link[@rel='acquisition']/@href"
        }
      }
    }

用 **XPath/JSONPath 子集**做提取，**不用 JS 表达式**。

### 5.3 Z-Library 的立场（这条我不能替你承担）

**事实**（来自 `docs/OPEN-QUESTIONS.md` Q5 的既有调研）：Z-Library 长期被美国司法部起诉、域名反复被查封、有运营者被逮捕；在中国大陆传播侵权电子书亦可能构成刑事犯罪；Apple/Google 商店政策明确禁止此类入口。

**我的建议（B 方案）**：
- **本仓库不包含、发布包不包含**任何 Z-Library 适配代码；
- 只提供**通用声明式书源框架** + 内置**合法源**（Gutenberg / Standard Ebooks / Open Library / Internet Archive / OPDS）；
- 用户可自行导入第三方规则 JSON，**风险由用户承担**；
- 商店版本**关闭第三方书源入口**；
- 文档与 UI 明确「仅供检索合法公开资源」。

**我预留接口但不提供实现。** 你要的「接入 Z-Library」如果坚持内置，需要你自己以私有补丁形式维护——我会把插件加载点设计好，但不会把代码放进这个仓库。

> ⚠️ 这一条需要你明确确认（见 §7 待决事项）。我不能替你承担法律风险，也不会假装这只是技术问题。

### 5.4 要补的工程点

1. **用户规则加载**：从 `book_sources` 读 `kind=user` 的规则，构造动态 `Searcher`。
2. **规则校验**：加载前静态校验（URL 必须 https、host 白名单、XPath 不能含函数调用、超时/大小上限强制）。
3. **SSRF 加固**：现有白名单是给内置源用的，**用户规则必须更严**——禁止内网 IP、禁止重定向到内网、DNS 重绑定防护。
4. **下载隔离**：从书源下载的文件必须过**格式校验 + 大小上限**，不能直接信任。

## 8. 成本估算（DeepSeek 官方价目，已核实）

> 来源：[DeepSeek 模型 & 价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)（抓取日期 2026-11-03）。
> 官方注明「空闲时段价格为高峰时段的一半」，高峰 = 北京时间周一至周五 9:00-12:00、14:00-18:00。

### 8.1 官方单价（人民币 / 百万 token）

| 项目 | deepseek-flash 空闲 | deepseek-flash 高峰 | v4-pro 空闲 | v4-pro 高峰 |
|---|---|---|---|---|
| 输入（缓存命中） | 0.02 元 | 0.04 元 | 0.15 元 | 0.30 元 |
| 输入（缓存未命中） | 1 元 | 2 元 | 4.5 元 | 9.0 元 |
| 输出 | 4 元 | 8 元 | 13.5 元 | 27.0 元 |

**选 flash**：翻译是高频大批量、质量要求「准确」而非「创作」，flash 足够且便宜 4 倍以上。
**v4-pro 只用于「歧义裁决」这类少量高价值判断**（§11.7，输入仅约 2 万 token，贵也贵不到哪去）。

### 8.2 整书翻译成本（30 万字中文书，flash）

估算口径（**这是估算，需用真实账单核实**）：
- 中文约 1.5 字/token → 30 万字 ≈ 20 万 token 正文
- 分块 prompt 开销（术语表 + 上下文）约 150 块 × 500 token ≈ 7.5 万 token
- 合计输入 ≈ **28 万 token**；输出（译文）≈ **20 万 token**

| 时段 | 输入成本 | 输出成本 | **合计** |
|---|---|---|---|
| 空闲 | 0.28 × 1 = 0.28 元 | 0.20 × 4 = 0.80 元 | **约 1.08 元** |
| 高峰 | 0.28 × 2 = 0.56 元 | 0.20 × 8 = 1.60 元 | **约 2.16 元** |

→ **单本整书翻译约 1~2 元人民币。**

### 8.3 人名归一化成本（同书，flash）

- 按章抽取：30 章 × 1 万字 ≈ 21 万 token 输入，输出候选列表约 2 万 token
  → 空闲约 0.21 + 0.08 = **0.29 元**；高峰约 0.42 + 0.16 = **0.58 元**
- 歧义裁决（§11.7 的混合方案）：输入仅约 2 万 token
  → 空闲 **约 0.01 元**，可忽略

→ **单本归一化不到 0.6 元。**

### 8.4 结论

**单本书「翻译 + 归一化」全做完，成本在 2~3 元人民币量级。**

真正的风险**不是单价，而是无限刷**：
- 若 `quota_ai_calls` 默认 1000 次/月，一个用户刷满 ≈ 1000 次翻译调用；
- 若每次都是整书任务，1000 次 × 2 元 = **2000 元/用户/月**。

→ **M5-1 的配额闸门是 P0，且必须按「token 用量」而非「调用次数」计费**（整书任务一次调用可能花 2 元，划词翻译一次只花几厘，按次数计费会严重失真）。
**这一条我要修正规划里的初稿**：原计划只提 `quota_ai_calls`（调用次数），不够——必须同时有 token/成本维度的配额。

> ⚠️ token 比例（1.5 字/token）是经验值，**未在本书上实测**。上线前应用真实书跑一次并核对账单。

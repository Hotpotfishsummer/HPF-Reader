# ADR-001 客户端选型：React vs Vue、Tauri v2 vs Wails v3

- 状态：**部分被取代**（2026-11-02：用户选择 Vue 3 + Wails v3，见 docs/ADR-002-客户端落地-Vue与Wails.md）。本文的证据与对比保留，作为复评依据。
- 日期：2026-11-02
- 触发：你问「为什么用 React 而不是 Vue」「为什么选 Tauri 而不是 Wails v3」
- 结论：**React 19 + Vite + Tauri v2**（推荐），并附「什么情况下应该改选」的明确条件

---

## 0. 先说方法论：这两个决策的可逆性完全不同

| 决策 | 可逆性 | 现在改的成本 | 定稿后改的成本 |
|---|---|---|---|
| 前端框架 React/Vue | **高**（可逆） | 0（还没写代码） | 中：重写 UI 层，但渲染内核与同步层不受影响 |
| 外壳 Tauri/Wails | **中**（半可逆） | 0 | 高：原生能力调用、构建发布链路、插件配置全部要重做 |

所以：**框架的选择应该主要听"人的熟练度"，外壳的选择才值得花力气论证。** 我把两者都摊开讲。

另外先给一个前提：**foliate-js 是框架无关的原生 ESM JavaScript**，渲染内核不含任何 React/Vue 代码。这意味着「React 还是 Vue」**不会**影响阅读器最核心的部分。

---

## 1. 决策一：React 19 而不是 Vue 3

### 我为什么默认选了 React（按权重排序）

1. **唯一的"生产级参照实现"是 React。** Readest 的前端是 Next.js 16.4.2 + React 19.2.8，其阅读器目录 app/reader 约 80 个组件、30 个 hooks（渲染、标注、脚注、笔记本、平行阅读、RSVP、AI 对话、翻译、搜索、TTS 全在里面）。我们一定会遇到它遇到过的边角问题——**同栈意味着可以直接对照它的解法**，而不是把问题重解一遍。
   证据：https://github.com/readest/readest/blob/main/apps/readest-app/docs/architecture.md（抓取 2026-11-02）

2. **保留 Q4 的选项。** 如果最终决定 fork Readest（AGPL 路线），React 让 UI 复用成本≈0；Vue 则等于把它的 80 个组件全部重写。**React 让"最坏情况下也有一条快路"仍然成立。**

3. **生态在本项目需要的几个点上是对等的**（这条不是决定性的，我不夸大）：
   - Radix 原语 → Vue 侧有 Reka UI（Radix 的 Vue 移植），基本对等；
   - TanStack Query → 有官方 Vue 适配；
   - Zustand → Vue 侧的 Pinia **其实更好**。

### Vue 的真实优势（我不粉饰）

- **SFC + 组合式 API 的开发体验更好**，样板更少；
- **Pinia 比 Zustand 更适合中大型状态管理**；
- 生态 churn 更小，升级更少踩坑；
- 我们这个项目 80% 的工作量是**局部 UI 状态**（设置面板、划词浮层、标注气泡、双栏切换）——这正是 Vue 响应式最舒服的场景。

### 结论与「什么情况下改选 Vue」

- **如果主力开发者（你）显著更熟 Vue，就应该选 Vue 3 + Vite + Pinia + Reka UI + VueUse**，其余选型一律不变（Tauri 壳、foliate-js 内核、后端、同步引擎都不动）。理由很简单：这个项目 80% 的工作量在 UI 交互与排版细节上，**人的熟练度 > 我的生态论证**。
- 现在切换成本 = **0**；定稿开工后切换成本 = 重写 UI 层。
- **我的判断**：如果你没有明确的 Vue 偏好，选 React（理由 1、2 是实打实的杠杆）。如果你有，选 Vue，我不会因此改任何架构设计。

## 2. 决策二：Tauri v2 而不是 Wails v3

### 先更正我自己的预设

我最初的直觉是「Wails 移动端不成熟」，**这个预设是过时的**：Wails v3.0.0 已于 **2026-10-26 正式 GA**（此前是近四年的 alpha）。所以下面的比较是拿**已 GA 的 Wails v3** 和 **Tauri v2 稳定版**比，不是拿它当半成品比。

证据：
- Wails v3.0.0 发布记录：https://github.com/wailsapp/wails/releases/tag/v3.0.0（发布 2026-10-26T11:15:13Z，非 prerelease）
- 已存在 v3.2.0-nightly（2026-11-01），周更节奏
- Tauri 2.0 稳定版公告：https://v2.tauri.app/blog/tauri-20/（2024-10-02，把 iOS/Android 写进 stable 的定义里）

### 对照表

| 维度 | Tauri v2 | Wails v3 (v3.0.0 GA) | 谁更好 |
|---|---|---|---|
| 桌面三平台 | 稳定 | 稳定（GTK4/WebKitGTK 6.0） | 平 |
| **iOS / Android** | 官方 stable 支持（2024-10 起），已有产品双端上架 | **官方标注 experimental，"isn't yet covered by the stability promise"** | **Tauri** |
| 渲染方式 | 系统 WebView | 系统 WebView | 平（**WebView 碎片化风险两者完全一样**） |
| **不可信内容隔离** | capability/权限体系 + IPC 重写 + 外部安全审计 | **自身发布说明列出：子 frame 可调用 /wails/runtime；Android 上 window.wails 暴露给所有 frame** | **Tauri（详见下）** |
| 后端语言 | Rust（+ 按需 Swift/Kotlin） | **Go** | **Wails**（Go 明显更好上手） |
| 插件/生态 | updater、fs、sql、deep-link、biometric、native-tts 等 + Readest 实战 | 内置 updater/签名/安装器/托盘，但移动侧生态尚薄 | Tauri |
| 参照实现 | Readest（六端，含为 e-ink WebView 写的 Kotlin 插件） | 无同量级阅读器先例 | Tauri |
| 包体 | 5–15MB 级 | 12MB 级 | 平 |

### 决定性理由 1：移动端成熟度（直接命中你的硬需求）

「网页 + 桌面 + 移动」是你的原始要求。Wails v3.0.0 发布说明原文写得很清楚：**iOS 和 Android 是 experimental，不在稳定性承诺范围内**（"Try it and tell us what you find; it isn't yet covered by the stability promise"）。而 Tauri 2.0 从 2024-10 起把 iOS/Android 列为 stable 定义的一部分，且 Readest 已经用它在 App Store 与 Google Play 上架。

选 Wails = 把「能不能上手机」从工程问题变成项目风险。这条单独就足以定案。

### 决定性理由 2：iframe 安全模型与「阅读器」身份直接冲突

Wails v3.0.0 的 Known limitations 原文（三平台通用 + Android 专项）：

- 所有平台：**绑定方法的调用从子 frame 走 HTTP 到 /wails/runtime，守卫不限制它们**；「把你嵌入的任何 iframe 都视为拥有你绑定的 Go 方法的访问权」；
- Android：**window.wails JavaScript 桥对所有 frame 暴露**，官方建议「不要把不可信的第三方内容嵌入应用的 WebView」，修复计划排在 3.0.1。

而**阅读器的本质就是把不可信的第三方内容（EPUB 自带的 HTML/CSS/JS）渲染进 iframe**。这不是"以后再优化"的小瑕疵，而是框架安全模型与产品核心场景的正面冲突。留给我们两个坏选择：要么每本书都当作可信代码（不可接受），要么放弃框架的绑定机制（等于放弃 Wails 的主要价值）。

Tauri 这边的情况：Tauri 对外部安全审计过、v2 重写了 IPC，并用 capability/权限体系控制暴露面。**但我不想在这里过度承诺** —— 安全结论必须靠实验，所以我在方案里加了一条硬性验收（见第 3 节）。

### Wails 的真实优势（同样不粉饰）

- **Go 比 Rust 好上手得多**，编译快、心智负担小、你本机已经能装 Go 而 Rust 工具链还没装；
- 构建发布是现成的：签名、NSIS/MSIX、DMG、AppImage、内置 updater（Tauri 侧要自己拼插件）；
- 单二进制、体积小、wails3 doctor / 模板齐全（含 React/Vue/Svelte），甚至有 MCP 服务可以让 AI 直接驱动调试。

**如果你是 Go 程序员且不在乎 e-ink 那批用户，桌面端用 Wails 是完全合理的。**

### 「什么情况下应该改选 Wails」

1. **放弃原生移动端**（只做桌面 + Web/PWA）。此时 Wails 最大的短板消失；
2. 并且接受「书籍内容不用 iframe 内嵌、改用独立渲染进程/窗口」的体验降级，或等它 3.0.1+ 修掉上述隔离问题。

这两条只要有一条不满足，我就不建议 Wails。**我的建议是：保持 Tauri v2 + React，但把 Wails v3 记为"若移动端被砍则重新评估"的备选**（写进 ADR 的复评条件）。

## 3. 这个讨论带来的一处方案升级（无论选哪个壳都要做）

对照 Wails 的已知问题，我们自己的隔离要求必须从"最佳实践"升级为**带验收标准的硬门槛**：

1. 书籍内容渲染在**独立 origin** 的 frame 中（不是与主应用同源），frame 带 sandbox 属性且**不授予 allow-same-origin**；
2. 原生能力（文件系统、网络、数据库、剪贴板）**只对主应用 frame 开放**，按 capability 最小授权；
3. 禁用一切书籍内嵌脚本（CSP script-src 'none'），并阻断书籍到外网的任意请求；
4. **M1 增加一个安全 PoC 验收项：从书本 iframe 内部尝试调用任意原生 API / 读取本地数据库，必须全部失败** —— 通过才算 M1 完成。

第 4 条以前只是我文档里的一句原则，现在它有了明确的失败判据。

---

## 4. 复评触发条件（什么时候该重开这个 ADR）

| 触发 | 动作 |
|---|---|
| M1 安全 PoC 失败（iframe 能触达原生能力） | 换隔离方案（独立 WebView/独立窗口渲染书籍），必要时重评外壳 |
| M2 Go/No-Go 发现 e-ink / 老 WebView 白屏无法绕过 | 评估移动端改原生双栈，或接受机型限制 |
| 你决定砍掉原生移动端 | **重新评估 Wails v3**（届时它的短板基本消失） |
| 你更熟 Vue | 只换前端框架，本文其余结论不变 |

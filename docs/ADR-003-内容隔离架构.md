# ADR-003 Wails 下的内容隔离架构（当前唯一阻塞项）

- 状态：**待决策（阻塞渲染层实现，不阻塞其他模块）**
- 日期：2026-11-02
- 一句话：在 Wails v3 上渲染第三方 EPUB 存在一条**默认配置下的真实越权通路**；必须先定架构，才能写渲染层代码。

## 1. 事实（全部为源码级证据，来自 task-4 / task-6）

| 发现 | 证据 | 后果 |
|---|---|---|
| 桌面/移动端对 /wails/runtime **零校验** | transport_http_notserver.go:1-13，checkRuntimeRequest 直接 return true；只有 server 构建校验 Origin | 任何能发 HTTP 的上下文都能调用全部绑定方法 |
| IPC 身份是 **window 级** x-wails-client-id 头，不记录帧来源 | application.go:390-402 | 子 frame 与主 frame **同身份** |
| 请求体不校验 Content-Type | transport_http.go:283-291 | opaque origin 可用「简单请求」直通副作用 |
| 无 token、无鉴权；**无 Origin 头的请求被放行** | 官方文档原文（curl 等非浏览器客户端 accepted） | 认证与授权必须我们自建 |
| **foliate-js 默认用最弱组合**：sandbox=allow-same-origin allow-scripts + srcdoc | paginator.js:783、885 | 默认配置下 srcdoc 是**同源**，且允许脚本 |
| 修复承诺挂在 v3.0.1，但 **v3.0.1 从未发布**；v3.1.0 发布说明无相关条目 | Releases / tags 实测 | 只能说「未验证到修复」，不能说已修复 |

## 2. 威胁链（一句话）

恶意 EPUB → 绕过净化或命中 WebView 解析缺陷 → 脚本在同源 iframe 内执行 → 直接 fetch http://127.0.0.1:PORT/wails/runtime → 以主窗口身份调用任意 Go 方法（读写本地文件、读写本地数据库、发起任意网络请求）→ **完全失陷**。

这不是理论推演：上述每一环都有源码或官方文档支撑，缺的只是「脚本执行」这一步——而它正是所有阅读器都靠**净化和 CSP** 来挡的。

## 3. 四个可选架构

| 方案 | 做法 | 保真度 | 安全强度 | 成本 | 可行性 |
|---|---|---|---|---|---|
| **A** opaque 内容帧 | 内容 iframe 用 sandbox=allow-scripts（**不给 allow-same-origin**），父帧用 postMessage 驱动 | 取决于 foliate-js 是否必须同源 | 高（结构性切断桥） | 若需自研分页则很高 | 待 task-7 核实 |
| **B** 阅读器窗口无桥 | 正文渲染在与资料库分离的窗口；自建中间件按窗口标识拒绝 /wails/runtime | 高（保留 foliate-js 全部能力） | 中高 | 中 | 待 task-7 核实 |
| **C** 同源 + 纵深防御 | 保留同源 iframe；DOMPurify 净化 + 逐节注入 meta CSP(script-src 'none') + 剥离远程引用 + 桥 token 门 | 最高 | 中（依赖净化与 CSP 无绕过；0day 即失陷） | 低 | 确定可行 |
| **D** 结构化渲染 | 只把 foliate-js 当解析器，转内部安全模型，用 Vue 组件渲染 | 低（丢复杂 CSS 排版与分页） | 最高 | 高 | 确定可行但代价大 |

> 参考：Readest 走的是 C 的弱化版（仅 DOMPurify 单层）；foliate-js 官方要求「必须用 CSP 阻断除 self 外的所有脚本」。也就是说 **C 是业界通行做法，不是我们的疏忽**，但要承认它的强度上限。

## 4. 我的建议（两步走）

1. **先花 2–3 天把 A/B 的可行性实测掉**（task-7 已给出核对清单，不写业务代码）。
   - B 可行 → 选 **B**（保真度与安全的最佳平衡）；
   - B 不可行、A 可行 → 选 **A**；
   - 两者都不可行 → 在 **C 与 D** 之间由你定。
2. **无论选哪条**，task-6 的 L1–L10 分层措施与 20 条 PoC 全部纳入 **M1 验收门禁**（其中 P-01 必须留「加固前成功」的证据，P-03 若出现副作用即 M1 不通过）。

## 6. 顺带记录：Web 版（Wails server 构建）必须做的改造

server 构建是 Wails 的真优势（go build -tags server 即出纯 HTTP 服务），但**不能直接暴露公网**：

| # | 必须做 | 原因 |
|---|---|---|
| B1 | 默认只绑 loopback，公网入口走自建反向代理 + 鉴权，或另建独立 HTTP API（不暴露 /wails/runtime） | 该端点无鉴权、非浏览器客户端被放行 |
| B2 | 自建用户/会话/配额模型 | server 模式把标签页当窗口（browser-N），无账号概念 |
| B3 | service 内禁止持有「当前用户/当前书籍」等请求级状态 | service 是跨所有窗口共享的单例 |
| B4 | Events 必须定向发送 | Go 侧 Emit 会广播到所有已连接浏览器 |
| B5 | 压低 /wails/runtime 请求体上限（默认 64 MiB） | 减小攻击面 |

## 7. 顺带记录：后端语言结论（推翻我的假设）

task-6 明确否掉了我提出的理由：若采用**服务端权威合并**，客户端只有 outbox + apply，**不存在第二份合并实现**，因此 Readest 的教训不适用，可共享的纯核心也只有约 500–1000 行。于是「外壳是 Go」**不构成**更换后端语言的充分理由，上一轮的 TS/NestJS 结论未被推翻。

Go 后端仍是**弱推荐**，理由换成：工具链已在、单二进制自托管、sqlc 与合并逻辑契合、内存更低。→ 决策权交给你，见 OPEN-QUESTIONS Q11。

## 9. 可行性核实结论（2026-11-02 更新，task-7）

### 9.1 Arch-A 判死（证据确凿）

| 事实 | 证据 | 后果 |
|---|---|---|
| foliate-js 访问 iframe 文档的**唯一入口**是 `get document() { return this.#iframe.contentDocument }` | paginator.js 字符偏移 @7829（全文件唯一一处 contentDocument） | opaque origin 下 contentDocument 为 **null** |
| `load(src, afterLoad, beforeRender)` 第一步就取 doc，随后 `getDirection(doc)` 解引用 `doc.defaultView` | @8006、@5860 | **直接抛异常——不是降级，是引擎整体不可用** |
| 依赖该 doc 的能力清单 | 分页 @9588/@9102、尺寸测量 @11240、书写方向 @5860、背景 @6032、页眉页脚 @6295、划词 @16493/@5597、CFI、高亮、脚注、字体 @8006 | 覆盖阅读器全部核心功能 |

→ **Arch-A（opaque 内容帧）不可行**，除非把 `View` 重写为「帧内 agent + postMessage」，即重写渲染引擎核心。**放弃 Arch-A。**

### 9.2 好消息：可达的隔离上限比预期高

| 事实 | 证据 | 意义 |
|---|---|---|
| foliate-js **完全不注入脚本**：`<script>` / `createElement('script')` / `document.write` 在 paginator.js 全文 **0 命中**；内容经 `iframe.src = blob:` 加载 | 源码全文检索 | **CSP `script-src 'none'` 不会破坏分页** —— 这是关键 |
| sandbox 里的 `allow-scripts` 只是为绕 WebKit Bug 218086 | README:79 | 若能去掉，可再上一层（L3） |
| 官方提供 **`transformTarget`** 钩子：EventTarget + `data` 事件，README:115 原文要求「Event handlers should mutate .data」；epub.js `createURL()` @23810 派发后**回读** `event.detail.data` 再 `createObjectURL` | README:115、epub.js @23810 | **唯一早于解析的变换点，零引擎改动**即可注入 meta CSP、剥脚本、重写 URL |
| 上游**不清理**书内脚本（epub.js 注释：TODO replace inline scripts, probably not worth the trouble） | epub.js @29072 | 净化必须我们做，且**必须做** |

→ **确定可达上限 = L2：同源 iframe + 逐节净化 + 逐节注入 meta CSP（script-src 'none'）+ 剥离重写远程引用**；L3 = 再去掉 allow-scripts（取决于 Bug 218086 是否仍必须）。

### 9.3 Arch-B 成立，但有 2 个生死门，且只是「爆炸半径控制」

| 事实 | 证据 | 后果 |
|---|---|---|
| `x-wails-client-id`、`x-wails-window-name` **由 JS 侧 fetch 自己填** | runtime.debug.js @4553/@4653 | **明确不可信**，不能作为授权依据 |
| `x-wails-window-id` 由**原生层**注入 | application.go:390-402（引自 task-6） | 若实现为 Header.Set（覆盖）→ 可信，Arch-B 成立；若「仅缺失时设置」→ 可伪造 → Arch-B 判死 |
| **帧粒度不存在**：同一 webview 内所有帧共享同一 window id | 框架不记录帧来源 | Arch-B 只能「按窗口限权」，**不能区分主帧与书帧** → 是爆炸半径控制，不是隔离 |

**生死门**：**C-01** 自建中间件是否真能拦到 /wails/runtime（挂载点 `AssetServerOptions.Middleware`，但中间件与 runtime handler 的执行顺序**未独立复核**）；**C-09** 从帧内伪造 `x-wails-window-id`，服务端看到的是真值还是伪造值。**任一失败 → 转 A5 结构化渲染。**

### 9.4 最终推荐架构（取代第 3 节的四方案并列）

| 层 | 措施 | 状态 |
|---|---|---|
| **L1 解析** | EPUB 解压预算（zip 炸弹防护）、XML 外部实体禁用 | 确定可达 |
| **L2 净化 + CSP（主力防线）** | 用 `transformTarget` 逐节：剥 script/on*/javascript:/foreignObject、重写远程 URL、注入 `meta CSP: default-src 'none'; script-src 'none'; img-src data: blob:; style-src 'unsafe-inline'` | **确定可达，零引擎改动** |
| **L3 沙箱收紧** | 去掉 iframe sandbox 的 allow-scripts（若 WebKit Bug 218086 允许） | 需实测 |
| **L4 爆炸半径控制（Arch-B）** | 阅读器窗口 + 中间件按 `x-wails-window-id` 拒绝 /wails/runtime | 需过 C-01/C-09 两门 |
| **L5 兜底退路（A5）** | 结构化渲染：foliate-js 只当解析器，Vue 组件渲染，彻底不嵌 HTML | 若 L4 两门失败即启用 |

> 诚实结论：**你选 Wails 是可行的**，但安全不能靠框架默认值——必须由我们自建 L2（确定可达）并尽力拿到 L3/L4。这与 Readest 走的路（仅 DOMPurify 单层）相比更严，因为我们的威胁模型里多了一条「桥零校验」。

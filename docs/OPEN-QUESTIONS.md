> **部分已确认（2026-11-02 你回复）**：✅ 可以跑 Docker ｜ ✅ 域名等已有现成的。
> 仍缺 4 项：**CPU/内存/磁盘/带宽**、**操作系统**、**服务器在中国大陆还是境外**（大陆需备案，且影响能否直连境外模型 API）、**是否已有对象存储或只能用本地磁盘**。
> 只要这几项不低于 4C8G + 200GB + 30Mbps，技术方案无需降级（Postgres + MinIO + Redis + Caddy 全部可上单机 Docker Compose）。

请提供：
1. 是否已有服务器？几个？**CPU/内存/磁盘/带宽**各是多少？
2. 操作系统与是否可**自行安装 Docker**？
3. 是否有**公网 IP + 域名 + HTTPS 证书**？域名是否已备案（大陆服务器必须）？
4. 服务器在**中国大陆还是境外**？（决定：是否备案、能否直连 Google/OpenAI、Z-Library 可达性）
5. 是否有对象存储（S3/阿里云 OSS/腾讯云 COS/MinIO）或只能用本地磁盘？

**为什么必须问**：书籍文件是**存储密集型**（1 万本书 ≈ 50–200GB），而 AI 与搜索是**计算/内存密集型**。若服务器只有 2C4G，我们必须把 AI 全部外包给 API、全文搜索降级为 Postgres FTS、不做本地模型；若连 Docker 都不能装，方案要整体换血。

**我的默认假设（若你暂不方便提供）**：4C8G 及以上 + Docker + 公网域名 + 100Mbps 以上带宽 + 本地磁盘 ≥ 500GB，境外或已备案。

## Q4. 代码策略：Fork Readest（AGPL）还是自研？

背景：Readest 已完成「全平台 + foliate 渲染 + 同步」的 90% 工作，但它是 **AGPL-3.0**，且强依赖 Supabase/Stripe/IAP。

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. Fork Readest 二次开发** | 最快（省 6–9 人月）；全平台构建链路现成；渲染/标注/TTS 都可用 | **整个项目必须 AGPL 开源**；要啃下 Turso WASM + Next.js 双路由 + Supabase 这套复杂架构；上游若重构则合并痛苦；替换其后端工作量不小 |
| **B. 参考架构、从零自研** | 许可自由（可闭源、可商用）；代码完全可控、结构更简单 | 慢得多（客户端 6–9 人月起步）；格式兼容坑要自己踩 |
| **C. 混合**：自研主程序 + 直接复用 **foliate-js（MIT，需最终核实）** 等宽松许可库 | 兼顾速度与许可自由 | 仍需自己搭全平台壳与同步 |

**我的推荐**：**C**。渲染内核用 foliate-js（若确认为 MIT/宽松许可），客户端壳与后端全自研，架构思路上大幅借鉴 Readest（Tauri v2 单代码库 + 本地 SQLite 副本 + 服务抽象层）。**只有在你能接受整个项目 AGPL 开源时才选 A。**

## Q5. Z-Library 与书源：做到什么程度？（法律风险最高的一项）

事实：Z-Library 长期被美国司法部起诉、域名被查封并更换（历史上多名运营者被逮捕），在中国大陆传播侵权电子书亦可能构成刑事犯罪；此外商店政策明确禁止此类功能。

| 选项 | 说明 | 风险 |
|---|---|---|
| **A. 完全不做书源** | 只做阅读器 | 风险最低，但少了你要的核心功能 |
| **B. 只做「书源插件框架」，官方不含任何侵权源**（内置仅 Gutenberg/Standard Ebooks/Open Library/Internet Archive/OPDS） | 用户可自行导入第三方规则 JSON | 中：风险主要转嫁用户，但**仍可能被认定为帮助侵权** |
| **C. B + 官方额外提供一个「Z-Library 插件」供用户手动安装** | 功能最贴合你的需求 | 高 |
| **D. 内置 Z-Library 搜索与下载** | 体验最好 | **极高**：法律 + 商店下架 + 项目/个人连带责任 |

**我的推荐**：**B**，并且：
- 规则引擎只支持声明式 JSON（不执行任意 JS），避免变成通用爬虫平台；
- 商店版本关闭第三方书源入口；
- 文档与 UI 明确「仅供检索合法公开资源」；
- Z-Library 的适配代码**不进入本仓库、不进入发布包**（若你需要，由你自行以私有补丁/插件形式维护，我可以在方案里预留接口但不提供实现）。

**请明确你的选择。这一条我不能替你承担。**

## Q10.（新增，阻塞项）内容隔离架构：先批准 2–3 天 Spike

**背景**：task-4/task-6 源码级证明——Wails v3 桌面/移动端对 /wails/runtime 零校验，IPC 身份是 window 级头且不记录帧来源；而 foliate-js 默认的 iframe 是 sandbox=allow-same-origin allow-scripts + srcdoc（同源且允许脚本）。两者叠加意味着：**默认配置下，恶意 EPUB 一旦获得脚本执行，就能调用我们全部导出的 Go 方法**。详见 docs/ADR-003-内容隔离架构.md。

**2026-11-02 可行性核实已收窄决策范围**（docs/ADR-003-内容隔离架构.md 第 9 节）：
- opaque 帧方案（原 A）**已判死**——foliate-js 访问内容的唯一入口是 iframe.contentDocument，opaque 下为 null，引擎直接不可用；
- **好消息**：foliate-js 完全不注入脚本，所以 `CSP script-src 'none'` 不会破坏分页；且官方 `transformTarget` 钩子是唯一早于解析的变换点，可零引擎改动地逐节净化 + 注入 meta CSP；
- 因此**主力防线（L2）确定可达**，剩下的只是「能否再上一层」。

**需要你回答（已大幅简化）**：
1. 是否批准 **1–2 天的收尾 PoC**，只验两个生死门：**C-01** 自建中间件能否真拦到 /wails/runtime；**C-09** 从帧内伪造 `x-wails-window-id` 服务端是否采信？→ 我建议**批准**。
2. 若这两个门任一失败，是否接受启用 **A5 结构化渲染**（放弃 foliate-js 的分页器，改为 Vue 组件渲染内部安全模型）？代价是复杂 EPUB 的 CSS 排版保真度下降。→ 我建议**接受作为退路**，且只对「不受信任来源」的书籍启用。

**需要你回答**：接受 Go 后端，还是保持 TypeScript？（两者都不影响已定的 API 契约与数据模型，且**早期可换**。）
